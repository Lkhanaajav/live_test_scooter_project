## User Constraints (from CONTEXT.md)

### Locked Decisions
### Preserve Existing Work
- Do not delete the recent template-approval, corridor, or fallback experiments.
- This phase must be additive and reversible.
- Existing planner modes should remain available for comparison.

### GPS Provides Maneuver Intent
- Vision should not decide whether the scooter should go left or right at an intersection.
- GPS or route logic provides `left`, `right`, or `straight`.

### Skeleton Is Not The Primary Turn Selector
- For commanded turns, do not use skeleton branches as the primary decision object.
- Skeleton-based logic may remain as a non-primary fallback for baseline comparison, but not as the main turn mode for this phase.

### Corridor-Supported Waypoint Target
- When intent is `left` or `right`, choose a waypoint target from the commanded-side drivable corridor, not from the raw outermost pixel and not from the whole-image extreme.
- The target should come from a forward decision zone where the turn opening is actually visible.
- Prefer the midpoint of commanded-side corridor support over unstable edge extrema.

### Smooth Controller-Ready Path
- The output path should be easy for the current controller to follow.
- The turn path should look like entry -> apex -> exit, not a crude frozen arc or a raw skeleton trace.
- The output contract must remain compatible with the existing controller and overlay pipeline.

### Maneuver Lock Must Be Sensible
- While a commanded turn is active and corridor evidence remains valid, the planner should not bounce back to `straight` or the opposite maneuver.
- But the path should not be frozen so rigidly that it cannot adapt to updated corridor evidence.

### Low-Confidence Failure Mode
- If a commanded-side waypoint target is not well-supported, emit low confidence plus slowdown/hold advice.
- Do not select an uncommanded maneuver just because it looks easier in the current frame.

### Claude's Discretion
- Exact target selection, scoring, and update logic can be decided during planning.
- The implementation may use waypoint smoothing, target hysteresis, corridor-side scoring, and staged entry/apex/exit shaping if needed.

### Deferred Ideas (OUT OF SCOPE)
- Do not replace the controller in this phase.
- Do not require a learned end-to-end planner.
- Do not fold in unrelated segmentation-model changes.
- Do not permanently remove skeleton code from the repo; just avoid depending on it as the main commanded-turn mechanism here.

## Summary

The repo already has most of the plumbing needed for this phase. `BEVPathExtractor.process()` is the stable public planner entry point, `PathPlanResult` already carries confidence and slowdown fields, `safe_corridor.py` already provides a DT-based centerline with width and confidence, and `realtime_nav_core.py` already contains an experimental manual endpoint/arc path that proves the repo can generate a turn without skeleton-first selection. The weakness is that the current endpoint logic is heuristic and brittle: it picks the extreme commanded-side span in a narrow band, clamps the endpoint hard, and does not formally score corridor support or exit geometry.

External planning patterns are consistent with the project direction. High-level route or command input should constrain local planning, not freeze a low-level path. Current navigation stacks still replan local geometry repeatedly around an updated goal or path, and research on command-conditioned driving and waypoint-conditioned planning consistently separates maneuver intent from local trajectory generation. For this repo, that means: `intent -> commanded-side corridor support -> stable waypoint target -> smooth path -> controller`.

The planning target should therefore be an additive waypoint-turn mode inserted ahead of graph-first selection for `left` and `right` intents only. Preserve `dt_corridor` behavior for no-intent and ordinary straight cases. For commanded turns, extract commanded-side support in a forward decision zone, pick a target by support/continuity score, fit a smooth path with an explicit apex and exit, and reject unsupported turns with low-confidence slowdown/hold instead of choosing a different maneuver.

**Primary recommendation:** Add a new target-first turn stage inside `BEVPathExtractor.process()` that uses commanded-side corridor support plus hysteresis to select an apex waypoint and optional exit waypoint, then validates the fitted path against the corridor before publishing it.

### Pattern 1: Command-Conditioned Side-Support Targeting
**What:** For `left` and `right`, search only the commanded side of the visible corridor inside a forward decision band, aggregate support across multiple adjacent rows, and choose a target from the midpoint of the best supported cluster.
**When to use:** Any frame with active commanded turn intent.
**Example:**
```python
# Pattern synthesized from Codevilla 2018, Talk-to-the-Vehicle 2019,
# Nav2 goal-updating docs, and this repo's current BEV planner.
if intent in {"left", "right"}:
    side_support = extract_side_support(corridor, dt_corridor, intent, decision_band_m=(1.8, 3.2))
    target = select_waypoint_target(
        side_support,
        prev_target=prev_turn_target,
        weights={"support": 0.40, "continuity": 0.25, "clearance": 0.20, "exit": 0.15},
    )
```

### Pattern 2: Two-Gate Approval
**What:** First gate the target itself, then gate the path fitted to that target. A target can be valid while the fitted path still clips the corridor on entry or exit.
**When to use:** Every commanded turn before publishing `PathPlanResult`.
**Example:**
```python
target_ok = target.support_score >= cfg.acquire_support_min
path_ref = build_turn_reference(ego, target.apex_m, target.exit_m)
path_ok = path_support_ratio(path_ref, corridor) >= cfg.path_support_min
if not (target_ok and path_ok):
    return low_confidence_hold_result(intent, corridor_confidence)
```

### Pattern 3: Maneuver Lock With Acquire/Sustain Thresholds
**What:** Use different thresholds to acquire a turn target versus to keep it. This is the simplest way to stop frame-to-frame bounce without freezing the geometry.
**When to use:** Consecutive frames during the same active `left` or `right` command.
**Example:**
```python
if prev_intent == intent and target.support_score >= cfg.sustain_support_min:
    active_target = blend_target(prev_target, target, alpha=cfg.target_update_alpha)
else:
    active_target = target if target.support_score >= cfg.acquire_support_min else None
```

### Pattern 4: Fit Entry -> Apex -> Exit, Then Refit To Controller Form
**What:** Build a short reference polyline with an explicit apex and optional exit anchor, then convert it into the controller's preferred cubic representation.
**When to use:** After target selection succeeds.
**Example:**
```python
anchors = np.array([
    [0.0, 0.0],
    target.apex_m,
    target.exit_m,
], dtype=np.float32)
reference_polyline = sample_piecewise_hermite(anchors)
controller_model = fit_regularized_cubic(reference_polyline)
```

### Anti-Patterns to Avoid
- **Outer-edge picking:** Do not use the outermost pixel, row extreme, or whole-image extreme as the turn target. That is exactly the instability the phase is trying to remove.
- **Intent overrides evidence:** The current template planner sorts intent-filtered left/right candidates by `abs(end_lateral_m)` after filtering. That is too rigid for this phase because it can prefer the sharpest turn even when support is weak.
- **Family-only hysteresis:** Holding only the maneuver family without holding target geometry invites lateral chatter and apex jumps.
- **Opposite-turn fallback:** For commanded turns, do not use graph or template fallback to silently choose the opposite side when support fails.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Local no-intent corridor recovery | A second custom centerline extractor | Existing `DtSafeCorridor` result in `safe_corridor.py` | This phase must preserve `dt_corridor` compatibility for no-intent behavior |
| Piecewise cubic interpolation | A bespoke spline package | Existing `_fit_regularized_cubic()` and, if needed, `scipy.interpolate.CubicHermiteSpline` | The repo already has controller-compatible cubic fitting, and SciPy is the standard fallback for multi-anchor cubic interpolation |
| Goal semantics from vision | Learned or heuristic left/right classifier in the planner | GPS/route intent from upstream | Locked decision: vision fits geometry, route logic decides maneuver |
| Full route graph or HD-map planner | A global planner inside this phase | Local waypoint-turn mode operating on the current BEV corridor | Scope is a short-horizon additive local planner, not full route generation |

**Key insight:** The hard part here is not generating a curve; it is deciding whether a commanded-side target is genuinely supported. Reuse existing corridor, DT, cubic, and fallback primitives, and spend the implementation budget on support scoring and turn-state logic.

## Common Pitfalls

### Pitfall 1: Choosing The Most Extreme Commanded-Side Span
**What goes wrong:** The selected target jumps to the outermost visible pocket or mask edge, especially when a turn opening first appears.
**Why it happens:** Single-row extremes are noisy and overreact to side pockets, clipped masks, and jagged segmentation.
**How to avoid:** Score contiguous commanded-side support across multiple rows and use a weighted median midpoint, not a single-row extreme.
**Warning signs:** Large target lateral jumps between adjacent frames; turn path starts by cutting toward the edge before settling.

### Pitfall 2: Approving A Target Without Approving The Path
**What goes wrong:** The apex point is inside the corridor, but the fitted curve leaves the corridor on entry or exit.
**Why it happens:** A single endpoint constraint is under-specified for turn shape.
**How to avoid:** Add an exit anchor when corridor evidence exists beyond the apex and always sample the fitted path against corridor bounds before publishing.
**Warning signs:** Good target support scores but low near-field containment; path clips corridor edge at 0.5-1.5 m forward.

### Pitfall 3: Intent Beats Evidence
**What goes wrong:** The planner commits to the sharpest left/right turn because the command says so, even when the commanded side is not yet visible.
**Why it happens:** Intent filtering is useful, but intent-only ranking without support gating is unsafe.
**How to avoid:** Keep intent as a hard side constraint, not as a license to bypass support and containment thresholds.
**Warning signs:** Turn starts too early, low corridor confidence coincides with strong lateral command, or unsupported turns never emit hold.

### Pitfall 4: Hysteresis Only On The Published Path
**What goes wrong:** The path looks smooth for a few frames, but the chosen target flips between different commanded-side clusters underneath.
**Why it happens:** Path smoothing hides target churn until the geometry diverges too much.
**How to avoid:** Persist the target state itself, use acquire/sustain thresholds, and blend target updates before the final path fit.
**Warning signs:** `path_source` stays stable but endpoint/apex diagnostics oscillate.

### Pitfall 5: Verification Assumes A Green Baseline
**What goes wrong:** Phase work is judged against a test suite that is already red.
**Why it happens:** Current repo state on 2026-03-23 already has unrelated failures.
**How to avoid:** Treat baseline failures as Wave 0 planning input. Either fix them first or explicitly isolate them from phase gating.
**Warning signs:** `python -m pytest tests -q` fails before any WPT changes are made.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Vision freely decides left vs right from local geometry | High-level route/command conditions the local planner | 2018 onward; reinforced by current navigation stacks | Keeps semantics upstream and local planning geometric |
| Skeleton or graph branch as primary turn object | Goal/waypoint-conditioned local trajectory generation inside a traversable corridor | 2019-2025 literature and robotics stacks | Better control over commanded maneuvers and smoother controller input |
| Single endpoint often used to resolve turn direction | Sparse multi-step route or apex+exit structure for tactical fidelity | 2025 literature | Single endpoint is usually enough for ambiguity resolution, but a second downstream anchor improves turn execution |
| Repo's current manual endpoint heuristic | Corridor-supported target + path dual gating | 2026-03-23 planning target | Reduces false commitments and makes unsupported turns fail safely |

**Deprecated/outdated:**
- Skeleton-first turn selection for commanded maneuvers: outdated for this phase because it conflicts with the locked intent-conditioning rule.
- Extreme-row endpoint picking: acceptable only as a short-lived experiment, not as the phase architecture.

## Open Questions

1. **Decision-band placement on representative turn videos**
   - What we know: the current heuristic prototype uses roughly 2.2 m +/- 0.55 m.
   - What's unclear: the best acquisition band for your June replay videos may differ by turn geometry and BEV crop.
   - Recommendation: plan a replay-tuning task early with logged target diagnostics and frame sheets.

2. **Best exit-anchor source**
   - What we know: `DtSafeCorridor` gives a stable centerline and width profile; row-wise corridor data gives commanded-side support.
   - What's unclear: whether exit should rejoin the DT centerline immediately or stay on a commanded-side midline longer through the turn.
