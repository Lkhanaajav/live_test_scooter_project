# Phase 11.1: GPS-intent corridor waypoint turn planner - Context

**Gathered:** 2026-03-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Add an alternative turn-planning mode for commanded maneuvers that is simpler and more controllable than skeleton-driven branch selection.

The phase should:
- keep no-intent behavior compatible with the current corridor-based straight-path behavior,
- accept GPS or route-provided maneuver intent (`left`, `right`, `straight`),
- for commanded turns, select a waypoint target from the visible drivable corridor on the requested side,
- fit a smooth controller-ready path from ego to that waypoint target,
- maintain the commanded maneuver through the turn while corridor evidence remains valid,
- emit low confidence and slowdown/hold guidance when the commanded turn is not yet visually supported.

The phase should not delete or replace the existing Phase 11 template-approval work. It is an explicit experimental alternative that must stay reversible.
</domain>

<decisions>
## Implementation Decisions

### Preserve Existing Work
- Do not delete the recent template-approval, corridor, or fallback experiments.
- This phase must be additive and reversible.
- Existing planner modes should remain available for comparison.

### GPS Provides Maneuver Intent
- Vision should not decide whether the scooter should go left or right at an intersection.
- GPS or route logic provides `left`, `right`, or `straight`.

### Skeleton Is Not The Primary Turn Selector
- For commanded turns, do not use skeleton branches as the primary decision object.
- Skeleton-based logic may remain as a non-primary fallback for baseline comparison, but not as the main turn mode for this phase.

### Corridor-Supported Waypoint Target
- When intent is `left` or `right`, choose a waypoint target from the commanded-side drivable corridor, not from the raw outermost pixel and not from the whole-image extreme.
- The target should come from a forward decision zone where the turn opening is actually visible.
- Prefer the midpoint of commanded-side corridor support over unstable edge extrema.

### Smooth Controller-Ready Path
- The output path should be easy for the current controller to follow.
- The turn path should look like entry -> apex -> exit, not a crude frozen arc or a raw skeleton trace.
- The output contract must remain compatible with the existing controller and overlay pipeline.

### Maneuver Lock Must Be Sensible
- While a commanded turn is active and corridor evidence remains valid, the planner should not bounce back to `straight` or the opposite maneuver.
- But the path should not be frozen so rigidly that it cannot adapt to updated corridor evidence.

### Low-Confidence Failure Mode
- If a commanded-side waypoint target is not well-supported, emit low confidence plus slowdown/hold advice.
- Do not select an uncommanded maneuver just because it looks easier in the current frame.

### Claude's Discretion
- Exact target selection, scoring, and update logic can be decided during planning.
- The implementation may use waypoint smoothing, target hysteresis, corridor-side scoring, and staged entry/apex/exit shaping if needed.
</decisions>

<specifics>
## Specific Ideas

- Reuse the Phase 11 corridor abstraction instead of rebuilding turn logic from skeleton graphs.
- For `left` or `right`, inspect a forward decision band in BEV and derive one or more commanded-side candidate targets from valid corridor rows.
- Score candidate waypoint targets by corridor support, near-field feasibility, continuity with the previous target/path, and early-turn usefulness.
- Fit a smooth path primitive from ego to the chosen target and rejoin the corridor after the turn rather than freezing a single harsh arc.
- Keep `dt_corridor` as the reference behavior for no-intent or unsupported-intent cases.
- Make experiments toggleable so the current stack, Phase 11 template approach, and this waypoint-turn approach can be replay-compared.
</specifics>

<deferred>
## Deferred Ideas

- Do not replace the controller in this phase.
- Do not require a learned end-to-end planner.
- Do not fold in unrelated segmentation-model changes.
- Do not permanently remove skeleton code from the repo; just avoid depending on it as the main commanded-turn mechanism here.
</deferred>
