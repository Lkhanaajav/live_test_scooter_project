## Summary

Phase 03.1 adds a second output channel from the existing YOLOv8-nano detector into the BEV
path-planning stack. Every YOLO detection already has a bounding-box foot point (bottom-center) in
image-pixel space. The homography matrix `H` (already loaded by `live_heading_demo.py`) maps any
image point to BEV pixel space with a single matrix multiply. From BEV pixels, the path extractor's
own `_metric_from_pixel()` gives metric (forward_m, lateral_m) coordinates in the same frame the
graph planner already uses. An exclusion zone around each projected foot point is therefore
trivially expressible in meters.

The two integration touch-points are:
1. `realtime_nav_core.py` — `process()` accepts an optional list of metric exclusion zones and
   `_score_candidates()` adds a penalty term for candidate paths that traverse them.
2. `live_heading_demo.py` — the orchestrator projects detections through `H`, converts to metric,
   and passes the result to `path_extractor.process()`.

A third, optional touch-point is `visualization.py` — `draw_bev_hud()` can render exclusion
ellipses as a debug overlay.

Temporal stabilization of the flickery YOLO bounding boxes is best handled with a lightweight
occupancy-grid EMA applied in BEV pixel space — consistent with how `TemporalMaskSmoother` already
stabilizes the segmentation mask, and requiring zero new dependencies.

**Primary recommendation:** Project foot-point through H to BEV, convert to metric, paint an
occupancy EMA grid in BEV space, then add a penalty term in `_score_candidates()` that sums EMA
values along each candidate path polyline. Keep the BEV mask approach (paint exclusion zones black)
as a hard-block fallback for OBSTACLE_STOP_M distances only.

### Pattern 1: Homogeneous Point Projection Through H

**What:** Map image-space foot point through the 3x3 homography to BEV pixel space.
**When to use:** Whenever a bounding box arrives from the detector.

```python
# Source: OpenCV perspectiveTransform docs + existing live_heading_demo.py line 596
import numpy as np
import cv2

def project_foot_to_bev(det: dict, H: np.ndarray) -> tuple[float, float] | None:
    """
    Project bounding-box foot point (bottom-center) from image space to BEV pixels.
    Returns (bev_x_px, bev_y_px) or None if behind the camera (w_bev <= 0).
    H: 3x3 float64 homography from load_bev_params()
    det: dict with 'bbox': (x1, y1, x2, y2)
    """
    x1, y1, x2, y2 = det["bbox"]
    foot_img = np.array([[(x1 + x2) / 2.0, float(y2)]], dtype=np.float64)  # shape (1,1,2)
    foot_bev = cv2.perspectiveTransform(foot_img.reshape(1, 1, 2), H)       # shape (1,1,2)
    bx, by = float(foot_bev[0, 0, 0]), float(foot_bev[0, 0, 1])
    return (bx, by)
```

**Critical detail:** `cv2.perspectiveTransform` accepts shape `(N, 1, 2)` float64. The output is
already in BEV pixel coordinates (same system used by `cv2.warpPerspective`). No additional
coordinate transform is needed.

**Why foot-point only:** Pinhole geometry — the bottom of the bounding box is the ground contact
point, which lies on the ground plane assumed by the homography. The rest of the box (above the
foot) does not lie on the ground plane, so projecting it would produce meaningless BEV locations.

### Pattern 2: BEV Pixel → Metric Coordinate (Existing API)

**What:** Convert projected BEV pixel to metric (forward_m, lateral_m) using BEVPathExtractor's
own coordinate system.
**When to use:** After Pattern 1, to express exclusion zones in the same frame as path candidates.

The existing private method `_metric_from_pixel()` (line 314 of `realtime_nav_core.py`) defines
the canonical conversion:

```python
# From realtime_nav_core.py lines 314-323 (exact copy, do not re-implement)
def _metric_from_pixel(self, pts_px, shape_hw):
    h, w = shape_hw
    u = pts_px[:, 0].astype(np.float32)
    v = pts_px[:, 1].astype(np.float32)
    forward = (float(h - 1) - v) / max(1.0, float(h - 1)) * self.cfg.bev_forward_m
    lateral = (u / max(1.0, float(w - 1)) - 0.5) * self.cfg.bev_lateral_m
    return np.stack([forward, lateral], axis=1).astype(np.float32)
```

**Key insight:** BEV image is (H=500px, W=600px) covering (forward=10m, lateral=10m).
So 1 BEV pixel ≈ 0.02m forward, 0.0167m lateral. Work grid is 220x220 covering the same metric
range; inside `_preprocess()` the BEV mask is resized to the work grid before metric conversion.

For the obstacle projection step (which runs in BEV image space, not work-grid space), apply the
same formula with `shape_hw = BEV_SIZE[::-1]` (height, width) = (500, 600):

```python
# BEV_SIZE = (600, 500) meaning (width=600, height=500)
BEV_H, BEV_W = 500, 600
forward_m = (BEV_H - 1 - bev_y_px) / (BEV_H - 1) * 10.0   # NAV_BEV_FORWARD_M
lateral_m = (bev_x_px / (BEV_W - 1) - 0.5) * 10.0          # NAV_BEV_LATERAL_M
```

### Pattern 3: EMA Occupancy Grid for Temporal Stabilization

**What:** A float32 grid in BEV space; each frame the grid is decayed and new obstacle
footprints are added as Gaussians or filled circles.
**When to use:** Between detection and path scoring to smooth flicker.

```python
# Analogous to TemporalMaskSmoother.smooth() in stabilization.py
class ObstacleEMAGrid:
    """
    Temporal EMA of obstacle footprints in BEV pixel space.
    Grid values in [0.0, 1.0]. Decays toward 0 each frame.
    """
    def __init__(self, bev_h: int, bev_w: int, alpha: float = 0.5,
                 footprint_radius_px: int = 15):
        self.grid = np.zeros((bev_h, bev_w), dtype=np.float32)
        self.alpha = alpha          # EMA weight for new frame
        self.radius = footprint_radius_px

    def update(self, foot_bev_pts: list[tuple[float, float]]) -> np.ndarray:
        """
        foot_bev_pts: list of (bev_x_px, bev_y_px) projected foot points (may be empty).
        Returns: current grid (H, W) float32 in [0,1].
        """
        new_frame = np.zeros_like(self.grid)
        for bx, by in foot_bev_pts:
            ix, iy = int(round(bx)), int(round(by))
            if 0 <= iy < new_frame.shape[0] and 0 <= ix < new_frame.shape[1]:
                cv2.circle(new_frame, (ix, iy), self.radius, 1.0, -1)
        # EMA: decay old, add new
        self.grid = (1.0 - self.alpha) * self.grid + self.alpha * new_frame
        return self.grid
```

**Alpha tuning:** The YOLO detection stride is typically 1 (every frame). If objects persist for
~5 frames, alpha=0.5 gives a half-life of 1 frame and ~3% residual after 5 frames — appropriate.
A higher alpha (0.7) reacts faster; lower (0.3) smooths more aggressively. Start with alpha=0.5.

**Footprint radius:** In BEV pixels, 1m ≈ 50px forward (BEV_H=500/10m) and ≈ 60px lateral
(BEV_W=600/10m). A person occupies ~0.4m width → radius ~12-15 BEV pixels. A car → ~1m →
~50px. Use class-specific radii (see config constants below).

### Pattern 4: Scoring Penalty in `_score_candidates()`

**What:** Add an obstacle penalty term to the existing cost sum.
**When to use:** In `_score_candidates()` after all existing terms are computed.

```python
# Proposed addition inside _score_candidates() after line 978 of realtime_nav_core.py
# obstacle_zones: list of (forward_m, lateral_m, radius_m) tuples, passed via self

def _obstacle_penalty(self, path_pts_m: np.ndarray) -> float:
    """
    Sum obstacle EMA values along the candidate path.
    Returns normalized penalty in [0, +inf), typically 0-3.
    """
    if not self.obstacle_zones:
        return 0.0
    penalty = 0.0
    for fwd_m, lat_m, rad_m, strength in self.obstacle_zones:
        # Check path points within obstacle radius
        d = np.sqrt((path_pts_m[:, 0] - fwd_m)**2 + (path_pts_m[:, 1] - lat_m)**2)
        overlap = np.sum(d < rad_m)
        penalty += overlap * strength
    # Normalize by path length
    return penalty / max(1.0, float(len(path_pts_m)))
```

The term is then added to `c.cost`:

```python
j_obstacle = self._obstacle_penalty(c.points_m)
c.cost += OBSTACLE_PENALTY_WEIGHT * j_obstacle  # new config constant, default 3.0
```

**Weight guidance:** Existing cost terms total roughly 0-8 for typical paths. An obstacle penalty
weight of 3.0 makes a fully-blocked path ~3-6 points worse than a clear path, which is sufficient
to prefer an alternative branch but not so large that it ignores all other factors.

### Pattern 5: Hard-Block at OBSTACLE_STOP_M Distance

**What:** For obstacles within `OBSTACLE_STOP_M` (1.0m, already in `config.py`), paint the BEV
mask black (exclusion zone) before passing to `process()`. This hard-blocks the path planner from
even considering routes through the zone.

```python
# In live_heading_demo.py, between detection and path extraction
STOP_ZONE_RADIUS_M = 1.2   # slightly larger than OBSTACLE_STOP_M
BEV_PX_PER_M = 50          # approximate from BEV_H / NAV_BEV_FORWARD_M

for det in detections:
    dist = det.get("distance_m", 999)
    if dist < OBSTACLE_STOP_M:
        bx, by = project_foot_to_bev(det, H_mat)
        radius_px = int(STOP_ZONE_RADIUS_M * BEV_PX_PER_M)
        cv2.circle(bev_sidewalk, (int(bx), int(by)), radius_px, 0, -1)
```

**When to use:** ONLY for very close obstacles (< OBSTACLE_STOP_M). Farther obstacles use the
scoring penalty (Pattern 4) to allow graceful re-routing.

### Anti-Patterns to Avoid

- **Projecting the full bounding box polygon:** All four box corners except the foot point are
  above the ground plane. Projecting them produces upward-slanting artifacts in BEV space.
- **Using `distance_m` from `estimate_obstacle_distance()` instead of BEV projection:** The
  monocular distance estimate is already an approximation; feeding it as an exclusion zone center
  forward-distance bypasses the homography and double-approximates. Always project through H.
- **Re-implementing metric coordinates:** The path planner has one canonical metric frame
  (defined by `_metric_from_pixel`). Exclusion zones must use the same frame. Do not define a
  second metric system from BEV_SCALE_PX_PER_M in config.py — that constant is from a different
  (older) coordinate system that does not match the work-grid scale inside `realtime_nav_core.py`.
- **Always masking the BEV black for all obstacles:** This prevents re-routing — the planner
  cannot score alternative branches if the obstacle zone removes sidewalk pixels that alternative
  paths depend on. Soft penalty (Pattern 4) for far obstacles, hard-block (Pattern 5) only for
  stop-distance.
- **Running projection in a separate thread:** The existing pipeline is single-threaded. Adding
  async projection introduces synchronization complexity for no measured gain at 8 Hz.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Homogeneous point projection | Custom matrix math | `cv2.perspectiveTransform()` | Handles division by w, clips correctly, consistent with `warpPerspective` output |
| Temporal smoothing | Frame-diff heuristics | EMA (same as `TemporalMaskSmoother`) | Already battle-tested in this codebase; same alpha semantics |
| Metric coordinate conversion | Separate pixel/m ratio | `_metric_from_pixel()` (existing) | Any custom formula will drift from the planner's internal frame |
| IOU tracking | SORT / ByteTrack | EMA grid | No dependency; sufficient at 8 Hz with small object count |

**Key insight:** The entire projection + exclusion pipeline can be built from NumPy array ops and
one `cv2.perspectiveTransform()` call. No new library is needed.

## Common Pitfalls

### Pitfall 1: BEV Coordinate System Mismatch

**What goes wrong:** Config.py defines `BEV_SIZE = (600, 500)` where 600 is WIDTH and 500 is
HEIGHT. Python/NumPy images are indexed as `[row, col]` = `[y, x]`. `cv2` functions use `(x, y)`
= `(col, row)`. Mixing these produces foot points that are mirrored left-right or upside-down
in BEV space.

**Why it happens:** `BEV_SIZE` follows OpenCV convention `(W, H)`, while `np.zeros(BEV_SIZE)`
would create a `(600, 500)` array (H=600, W=500) — the opposite! The actual shape used is
`np.zeros((BEV_SIZE[1], BEV_SIZE[0]))` = `(500, 600)`. `bev_sidewalk.shape` returns `(500, 600)`.

**How to avoid:** Always extract `bev_h, bev_w = bev_sidewalk.shape[:2]` from the actual array,
not from `BEV_SIZE`. When passing to `cv2.circle` or `cv2.perspectiveTransform`, use `(x, y)`
order (column first). When indexing with NumPy, use `[row, col]` (y first).

**Warning signs:** Projected obstacle appears on the wrong side of BEV center. Test: a person
standing directly in front of the camera (bbox centered at `frame_w/2`) should project to near
`bev_x = bev_w/2`.

### Pitfall 2: Obstacle Behind the Homography Plane

**What goes wrong:** For very close obstacles (< 1m), the bounding box foot may fall below the
vanishing-point horizon. The homography projects these to `w_bev < 0` (behind the camera),
producing a BEV point with enormously negative or positive pixel coordinates that falls entirely
outside the BEV image.

**Why it happens:** The homography is calibrated for the ground plane visible in the camera
frustum. Objects at the very bottom of the image (< 0.5m from the camera) may clip outside the
calibrated region.

**How to avoid:** After projection, check `0 <= bx < bev_w and 0 <= by < bev_h` before use. For
out-of-bounds projections, clamp to the nearest BEV boundary (ego vicinity) rather than discarding
— the obstacle is so close it definitely overlaps the ego's immediate path.

### Pitfall 3: Flicker Causes Phantom Obstacles

**What goes wrong:** YOLO misses a person for 1-3 frames, the EMA grid decays to 0 in that window,
then the detection returns and the penalty jumps back. The path alternates between blocked and clear
on every other frame, causing heading oscillation.

**Why it happens:** Alpha=1.0 (no EMA, instantaneous) would cause maximum flicker. YOLO on CPU at
8 Hz with small objects has 10-30% miss rate per frame.

**How to avoid:** Use alpha=0.5 so the grid retains 50% residual after 1 missed frame (vs. 0%
with no EMA). The grid fully clears in ~5 frames of no detection, which is acceptable. Do NOT set
alpha < 0.3 — the grid responds too slowly and the system "sees" phantom obstacles long after
removal.

**Warning signs:** Heading oscillates ±5-10 degrees with a stationary obstacle in view. Run with
`--log` and inspect `has_path` column.

### Pitfall 4: Work-Grid vs. BEV-Image Coordinate Confusion

**What goes wrong:** The path planner resizes the BEV mask from `(500, 600)` to the work grid
`(220, 220)` in `_preprocess()`. Exclusion zones expressed in BEV-image pixels must be either:
(a) expressed in metric (forward_m, lateral_m) so they work regardless of grid resolution, or
(b) re-projected to work-grid pixels when scoring.

Using metric coordinates (Pattern 4) avoids this entirely because `_score_candidates()` already
operates on `points_m` in metric space.

**How to avoid:** All exclusion zones stored in `self.obstacle_zones` MUST be in metric (forward_m,
lateral_m, radius_m). Never store pixel coordinates from either the BEV image or the work grid in
that list.

### Pitfall 5: Obstacle Partially Off Sidewalk Silently Penalizes Correct Path

**What goes wrong:** An obstacle is detected at the sidewalk edge (a parked bicycle on the edge).
The BEV projection places the foot point at the edge of the sidewalk mask. The penalty term fires
on the one candidate path that goes along the edge, even though there is no viable alternative
branch.

**Why it happens:** Penalty is applied uniformly without checking whether an alternative path
actually exists.

**How to avoid:** Only apply the penalty if `len(candidates) >= 2`. If there is only one
candidate, skip obstacle penalization (the planner has no choice anyway). The speed-reduction path
(existing `OBSTACLE_CLOSE_M` logic in `compute_speed()`) still fires independently to reduce
velocity.

### New: Projection + Metric Conversion (complete flow)

```python
# Source: derived from above — not yet in codebase
import cv2, numpy as np
from config import NAV_BEV_FORWARD_M, NAV_BEV_LATERAL_M

def detection_to_metric(det, H, bev_mask_shape):
    """
    det: dict with 'bbox': (x1,y1,x2,y2)
    H: 3x3 homography (image -> BEV pixels)
    bev_mask_shape: (H_px, W_px) e.g. (500, 600)
    Returns: (forward_m, lateral_m) or None if out of bounds.
    """
    x1, y1, x2, y2 = det["bbox"]
    foot = np.array([[[(x1 + x2) / 2.0, float(y2)]]], dtype=np.float64)
    bev_pt = cv2.perspectiveTransform(foot, H)[0, 0]
    bx, by = float(bev_pt[0]), float(bev_pt[1])
    bev_h, bev_w = bev_mask_shape[:2]
    # Clamp to BEV boundary (very close obstacles may project outside)
    bx = float(np.clip(bx, 0.0, bev_w - 1))
    by = float(np.clip(by, 0.0, bev_h - 1))
    forward_m = (bev_h - 1 - by) / (bev_h - 1) * NAV_BEV_FORWARD_M
    lateral_m = (bx / (bev_w - 1) - 0.5) * NAV_BEV_LATERAL_M
    return forward_m, lateral_m
```

## Open Questions

1. **Calibration mismatch effect on projection accuracy**
   - What we know: The BEV homography is currently ill-conditioned (cond=1.1e+06). Obstacle
     foot points projected through a bad H will land in wrong BEV locations.
   - What's unclear: How large is the positional error in meters for a 1m distance error in the
     BEV warp? With 93% pixel loss in BEV, the EMA grid may be mostly in empty BEV space.
   - Recommendation: Implement Phase 03.1 now. After Phase 2 BEV recalibration, validate that
     projected obstacle positions are visually correct on the BEV overlay. The code is correct
     either way; the quality improves when H is fixed.

2. **Detection stride vs. obstacle persistence**
   - What we know: `detection_stride` can be set to 2 or 3 in low-power mode, meaning YOLO runs
     every 2-3 frames. The EMA grid is updated every frame (including skipped detection frames).
   - What's unclear: On frames where detection is skipped, should the EMA decay or hold?
   - Recommendation: Decay on all frames regardless of detection stride. Update with empty
     `foot_bev_pts=[]` when detection is skipped. This is conservative (faster obstacle clearance)
     and simpler to implement.

3. **Obstacle behind ego (rear detections)**
   - What we know: YOLO detects objects in the full image including behind the scooter if the
     camera has a wide FOV. The BEV homography maps only the forward ground plane.
   - What's unclear: How often do non-forward objects produce valid (positive forward_m) BEV
     projections vs. out-of-bounds projections?
   - Recommendation: Filter out any projected foot point with `forward_m < 0.3` (less than 30cm
     forward) as these are either behind ego or at the very edge of the ground plane. This also
     avoids penalizing the ego's own standing position.
